# Owner loading and order notification fixes — 28 November 2026

This change uses the existing React/RTK Query, Socket.IO, Express and MongoDB
stack. It adds no service, dependency, paid cache, queue, replica or hosting
upgrade. The repository's existing single-instance Northflank/Caddy deployment
can build it normally. No live deployment or production data changes were made.

## What caused the symptoms

The owner has many more prefetched and saved screens than employees. Every
successful write published an unqualified change event; even marking a
notification read invalidated all saved screens. Each closed cache entry then
started its own background refresh. Those requests shared a 450-request,
15-minute account budget with session, revision and inbox reads. The client
also suppressed all reads during that cooldown. This explains how an owner
could show old notifications and missing dashboard/POS data while employees
on separate account budgets remained current. The screenshots show the 429s;
production logs were not available to attribute the exact request sequence.

Checkout also saved notifications after committing the order, logging and
swallowing notification persistence failures. That separate failure path could
acknowledge an order without creating its inbox record.

## Resulting behavior

- Checkout commits the order, stock reservation, owner/team inbox records and
  tenant change counters in the same MongoDB transaction. Inbox records are
  inserted in one batch. Socket messages are emitted only after commit.
  Idempotent retries return the original order without duplicate notifications
  or another revision increment.
- Server change events and durable counters identify affected cache domains.
  Notification read receipts affect the recipient's inbox, not the shop's
  catalog, accounts or reports. Unknown write routes and backup restores use
  an explicit full-invalidation fallback.
- The five-minute full data download and recurring identity polling are gone.
  A visible tab checks small change counters at most once a minute, also on
  connection recovery. Business reads run only for changed domains or temporary
  failures. Initial saved snapshots are reconciled once when their revision is
  unknown; socket reconnection also recovers operational lists and inboxes.
- Closed-page invalidations are deduplicated and drained serially. Reconciliation
  prioritizes visible subscriptions and retains saved data. Pending reads and
  temporary failures do not advance the revision checkpoint. Permission denials
  are not retried indefinitely.
- Signed business accounts have separate bounded page and live-read budgets:
  240 and 120 requests per minute respectively. Login, refresh, POS, reports,
  uploads and payment-specific limits remain in place. Anonymous traffic cannot
  select a business budget. Client cooldowns respect the same separation.
- A missing throttled view shows a countdown and retries after Retry-After;
  it no longer incorrectly tells an online user to connect to the internet.
- Additive notification indexes support personal inbox pagination, shared
  legacy owner records and stable timestamp/ID sorting. Startup waits for order,
  notification and revision model initialization. Graceful shutdown drains
  pending revision publications before disconnecting MongoDB.

Existing bounded pagination, catalog/inventory indexes, database-side filtering,
lazy route chunks, browser query caching, IndexedDB snapshots, compressed assets
and immutable hashed-asset caching remain in use. Financial writes continue to
require authoritative server confirmation.

## Verification

- All 140 client tests passed. Saved-data/revision tests were rerun after the
  final checkpoint handling adjustment: 15 passed.
- Across the server suite, all 160 cases passed. The broad run had 158 passes
  and two five-second timeouts while browser checks were running. Both timed-out
  cases passed on isolated rerun in about 1.3 seconds each; no assertions changed.
- Five production-build Chromium scenarios passed across the final runs:
  owner notification during page throttling and dashboard/POS recovery, staff
  and packer live work, delivery with independent read state, and missed-event
  recovery after reconnection. The new owner test initially used an incorrect
  exact-text locator for a dashboard line that includes a timestamp; correcting
  that locator made it pass without changing application behavior.
- Transaction fault injection confirms an inbox write failure rolls back order,
  stock and ledger writes. Retrying the same submission commits once. Parallel
  customer submissions create one owner notification and one per active worker.
- A six-minute unchanged-data test performs six tiny counter reads and zero
  product-page downloads. An unrelated expense counter change still downloads
  zero product pages; a product change downloads the product page once.
- `node scripts/performance-notifications.js` uses a disposable database with
  3,000 notifications. A 20-row owner inbox examines 40 documents; a worker inbox
  examines 20. Neither uses a blocking sort. The owner query originally examined
  2,000 documents and sorted them before the tenant timeline index was added.
  These are local query-plan measurements, not Northflank latency/load claims.
- Production build and ESLint passed; ESLint reports the three existing layout
  Fast Refresh warnings and no errors. Changed server files pass syntax checks.

Reproduce the targeted browser checks with the existing production build setup:

```powershell
cd client
$env:VITE_API_URL='/api/v1'
$env:VITE_WS_URL=''
$env:VITE_DISABLE_WEBSOCKETS='false'
npm run build
$env:STOREFRONT_PRODUCTION='true'
$env:STOREFRONT_OFFLINE_FONTS='true'
npx playwright test --config playwright.storefront.config.js realtime-work.spec.js --workers=1
```

Database edits outside the API must also publish appropriate change counters;
the removed periodic full download no longer masks unannounced direct writes.
The new checkout path records its tenant counter atomically. Other API mutations
retain the existing post-response revision publisher, with shutdown draining and
logged failures. This change does not introduce distributed socket delivery or
distributed rate-limit storage for multiple API replicas.

## Follow-up maintainability and regression review

Removed the unused legacy `notifyTeam` helper after confirming it had no callers.
Revision increments now have one implementation in `syncRevision.service.js`,
shared by checkout transactions and the response middleware. Checkout no longer
imports a business write helper from HTTP middleware.

The review found an actual cache invalidation omission: owner storefront order
updates could settle COD payments without notifying cached Day Close and receipt
screens. A new owner COD handover integration test failed before the fix. The
order dependency map now includes DailyClosing, Transaction and POS counters.
That test and 25 related request-budget, assignment/inbox, idempotency and saved
revision cases pass after the cleanup (26 total). Changed server files also pass
syntax checks and the diff has no whitespace errors. This follow-up did not
change frontend rendering or deploy the service.
